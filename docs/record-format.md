# 記録形式（第2版）

このファイルは、作業記録の項目と書式の定義です。いつ、どこに記録するかは `AGENTS.md` に書いてあります。

ここに書いた形式は `scripts/build_index.py` が読み取り、`STATUS.md` と索引の生成、形式の検査に使います。形式がずれると自動生成や検査が正しく動かないため、項目名、見出し、IDの形は、この定義のとおりに書きます。

## 1. ファイルの構成

```text
themes/
└─ <テーマID>/
   ├─ README.md              自動生成（編集しない）
   ├─ <エントリID>.md        要約エントリ
   └─ verbatim/
      └─ <エントリID>.md     原文
```

- 1つのエントリを1つのファイルにします。ファイル名はエントリIDと同じです。
- 原文ファイルは、要約エントリが原文を参照するときだけ作ります。
- エントリと原文は、保存した後に編集しません。訂正は新しいエントリで行います（§6）。

## 2. IDと名前

| 対象 | 形式 | 正規表現 | 例 |
|---|---|---|---|
| テーマID | 作成日-名前 | `^\d{8}-[a-z0-9][a-z0-9-]{1,29}$` | `20261102-preprocess` |
| セッションID | S-日付-ランダム4文字 | `^S-\d{8}-[a-z0-9]{4}$` | `S-20261102-a1b2` |
| エントリID | 日時-ランダム4文字 | `^\d{8}T\d{4}-[a-z0-9]{4}$` | `20261102T1015-k3p9` |

- 日付と日時は日本時間です。セッションIDの日付は、会話を始めた日です。
- ランダム4文字は英小文字と数字から選びます。同じテーマのフォルダに同じIDがないことを、保存前に確かめます。
- テーマIDの名前の部分は、英小文字・数字・ハイフンで2〜30文字です。ユーザーの題名から短く作ります（例：「測定ログの前処理」→ `preprocess`）。
- テーマをまたぐ記録は `themes/_project/` に置き、`theme` を `_project` にします。無人の実行で記録先が分からなかった記録は `_unsorted` です。
- 本文や会話でエントリを指すときは、末尾の4文字だけでもかまいません（例：`k3p9`）。項目には完全なIDを書きます。

## 3. 冒頭の項目

エントリの先頭に、`---` で囲んだYAMLを書きます。すべての項目を、下の順で毎回書きます。値がない項目は `null` または `[]` にします。項目がそろっていると、抜けを機械的に見つけられるためです。

| 項目 | 値 | 内容 |
|---|---|---|
| `id` | エントリID | ファイル名と同じ |
| `format` | `2` | この記録形式の版 |
| `title` | 文字列 | 日本語の短い題名（40字程度まで） |
| `theme` | テーマID | エントリを置いたフォルダ名と同じ |
| `theme_title` | 文字列 または `null` | テーマの日本語の題名。新しいテーマの最初のエントリだけに書き、ほかは `null` |
| `session` | セッションID | この会話のID |
| `type` | `work` `review` `decision` `summary` `note` | エントリの種類（§4） |
| `prev` | エントリID または `null` | 同じセッションの直前のエントリ。セッションの最初は `null` |
| `forked_from` | エントリID または `null` | 別の会話から分岐して始めたときの分岐元 |
| `based_on` | エントリIDのリスト | 前提にした、ほかのセッションのエントリ |
| `supersedes` | エントリIDのリスト | このエントリで置き換える古いエントリ |
| `refs` | エントリIDのリスト | review と decision の対象 |
| `author` | `{tool, mode, model}` | 内容を書いた者 |
| `recorded_by` | `{tool, mode}` | 保存した者 |
| `created` | 日時 | `2026-11-02T10:15+09:00` の形 |
| `commits` | コミットハッシュのリスト | 関係するコードや設定のコミット（7文字以上）。記録ファイルだけのコミットは書かない |
| `artifacts` | `{name, path, url}` のリスト | Driveの成果物 |
| `verbatim` | パス または `null` | 原文ファイル（`verbatim/<エントリID>.md`） |

author と recorded_by

- `tool`：ツールの名前です（例：`ChatGPT` `Claude` `Gemini` `Codex` `Claude Code` `Gemini CLI` `Copilot`）。ユーザー自身が書いた場合は `human` です。
- `mode`：ツールでの呼び名をそのまま書きます（例：`Chat` `Work` `Deep Research` `通常`）。特にない場合は `通常` です。
- `model`：author だけに書きます。分からなければ `不明` です。AIの自己申告は正確でないことがあるためです。

artifacts

- `name`：日本語の名前と版（例：`前処理集計 v01`）
- `path`：Driveのプロジェクトフォルダからのパス
- `url`：ファイルIDを含む `https://` のURL。移動や名前変更をしてもリンクが切れないためです。

```yaml
artifacts:
  - name: 前処理集計 v01
    path: 03_sheets/20261102T1140-q8m1_前処理集計_v01.xlsx
    url: https://drive.google.com/file/d/<FILE_ID>/view
```

`created` は人が読むための目安です。記録の正確な順序は、コミット時刻で判断されます。

## 4. 種類ごとの本文

本文の見出しは、種類ごとに下の名前と順番で書きます。書くことがない見出しも残し、「なし」と書きます。見出しがそろっていると、`STATUS.md` やテーマのREADMEを自動で作れるためです。

どの種類にも共通する書き方

- ユーザーの発言とAIの解釈を分けて書きます。判断の根拠になった発言は「」で引用し、（原文 §1）のように原文の場所を添えます。
- 要点を短く書きます。長い説明、ログ、会話のやり取りは原文に置きます。
- 「次にやるとよいこと」のような提案は書きません。

### work（作業）

| 見出し | 書くこと |
|---|---|
| `## 依頼` | 何を頼まれたか（要点）と原文の場所 |
| `## 経緯` | 依頼の変更、方針の選択、ユーザーの指示が `AGENTS.md` と食い違ったこと |
| `## 実施内容` | 実際にしたこと。作ったファイル、変えたファイル |
| `## 判断と理由` | 作業の中で選んだことと理由。ユーザーの選択なら発言を引用 |
| `## 主張` | この作業から言えること |
| `## 証拠` | 主張を確かめた方法と結果（実行結果、数値、ファイル） |
| `## 未解決・残作業` | 終わっていないこと、未検証のこと、既知の問題 |

証拠には、実際に確かめたことだけを書きます。確かめていないことは、「未解決・残作業」に「未検証：…」として書きます。

### review（意見）

| 見出し | 書くこと |
|---|---|
| `## 対象` | レビューしたエントリ、ファイル、成果物 |
| `## 確認範囲` | 読んだもの、実行したもの、確認できなかったもの |
| `## 指摘` | 番号付きの指摘 |

```markdown
1. 【重要】連続欠損の長さに上限がなく、長い欠損区間も補間されている。
   根拠：src/preprocess.py の補間処理に上限の指定がない。
```

- 重要度は `【重要】` `【中】` `【軽微】` の3段階です。
- 根拠には、確かめた場所（ファイル、行、表のシートなど）を書きます。
- `refs` にはレビューの対象のエントリIDを書きます。空にはしません。
- 指摘は意見です。作業で従うかどうかは decision で決まります。

### decision（判断）

| 見出し | 書くこと |
|---|---|
| `## 対象` | 何についての判断か（レビュー、次の作業、方針） |
| `## 判断` | 決まったことを項目ごとに |
| `## 判断した人` | `ユーザー` |
| `## ユーザーの発言` | 判断を示した発言の引用 |

```markdown
- 指摘1：採用（連続欠損の上限は4件）
- 指摘2：見送り（測定期間が1か月のため）
- 指摘3：保留（データの追加を待つ）
- 予定：解析報告の作成に進む
```

- decision はユーザーの判断だけを記録します。AIだけで決めたことは work の「判断と理由」に書きます。
- 使う場面は、レビューの採否、次にやること、テーマをまたぐ方針の3つです。
- レビューへの判断では、`refs` にレビューのエントリIDを書き、指摘ごとに `採用` `見送り` `保留` のどれかを書きます。`保留` が残るレビューは、`STATUS.md` の「判断待ち」に残ります。
- 次にやることは `予定：` で始めます。

### summary（まとめ）

| 見出し | 書くこと |
|---|---|
| `## 現状` | どこまでできているか |
| `## 未解決・残作業` | 終わっていないこと、未解決の問題 |
| `## 決定済みの予定` | decision で決まった次にやること。decision のIDを添える |

- 1つのテーマについて書きます。テーマをまたぐまとめは `themes/_project/` に書きます。
- `based_on` に、まとめの元にしたエントリを書きます。
- `STATUS.md` には、テーマごとに最新の summary の3つの見出しの中身がそのまま載ります。それだけ読んでも現状が分かるように書きます。
- 「決定済みの予定」に書けるのは、decision で決まったことだけです。

### note（その他）

| 見出し | 書くこと |
|---|---|
| `## 内容` | 調べたこと、検討したこと、メモ |
| `## 出典` | 参照したページ、ファイル、エントリ |

## 5. 原文ファイル

```markdown
# 原文 20261102T1015-k3p9

## §1 依頼（ユーザー）
Driveの 05_data/raw/20261020_測定ログ.csv の欠損値と外れ値を確認して、前処理の方針を一緒に決めたい。

## §2 方針の決定（ユーザー）
Aで。除外した行は、一覧を別に出して残して。

## §3 実行ログ（抜粋）
$ python src/preprocess.py --sample 100
interpolated: 2 rows / removed: 1 row
```

- 見出しは `## §番号 内容（発言者）` の形です。発言者は `ユーザー` `AI` `ログ` `資料` のどれかです。
- ユーザーの発言は、句読点や表記も含めてそのまま書きます。
- ログや出力は、主張の確認に必要な部分だけを抜き出し、見出しに（抜粋）と添えます。
- 会話の全文は入れません。全文が必要なときは Drive の `06_transcripts/` に置き、要約エントリの `artifacts` に加えます。
- APIキー、パスワード、個人情報は `［伏せ字：APIキー］` のように置き換えます。

## 6. 訂正と分岐

| 場面 | 書き方 |
|---|---|
| 内容を訂正する | 新しいエントリを作り、`supersedes` に古いエントリIDを書く。古いファイルは残す |
| 結果を使わないことにした | `note` を作り、`supersedes` に対象のエントリIDを、本文に理由を書く |
| 同じ会話でプロンプトを編集した | 何もしない。同じ `prev` を持つエントリが2つになり、自動で分岐として検出される |
| 別の会話に分岐した | 新しいセッションIDにし、`prev: null`、`forked_from` に分岐元のエントリIDを書く |

## 7. コミットメッセージ

```text
<1行目：変更の要約>

<本文（任意）>

Entry: <エントリID>
```

- 末尾の `Entry:` 行は、コードのコミットにも記録ファイルのコミットにも書きます。
- 記録ファイルだけのコミットは、1行目を `記録: <title>` にします。このコミットは、エントリの `commits` には書きません。
- 複数のファイルを1つのコミットにまとめられるツールでは、まとめてかまいません。

## 8. Driveのファイル名とフォルダ

```text
<エントリID>_<内容>_v<2桁の版>.<拡張子>
例：20261104T1045-r5t8_前処理集計_v02.xlsx
```

- 先頭は、その版を作ったエントリのIDです。版を上げるときは、新しいエントリのIDで新しいファイルを作ります。
- 内容は日本語でかまいません。空白は `_` にし、`/ \ : * ? " < > |` は使いません。
- 古い版は `99_archive/` に移します。削除はしません。
- Googleドキュメント・スプレッドシート・スライドは、同じファイルを上書きし、版の番号は付けません（`<エントリID>_<内容>`）。名前の先頭は最初に作ったエントリのIDのままにし、更新したエントリの `artifacts` にも同じURLを書きます。

| フォルダ | 置くもの |
|---|---|
| `01_docs/` | Word、PDF、Googleドキュメント |
| `02_slides/` | スライド |
| `03_sheets/` | 表計算 |
| `04_images/` | 画像、図の書き出し |
| `05_data/raw/` | 取得したままのデータ（変更しない） |
| `05_data/processed/` | 加工後のデータ |
| `05_data/reports/` | 出力付きノートブックの書き出し |
| `06_transcripts/` | 会話の全文、長いログ |
| `99_archive/` | 差し替えた旧版 |

## 9. 自動で判定されること

次のことは項目として書きません。`scripts/build_index.py` がエントリから判定します。

| 判定 | 方法 |
|---|---|
| 置き換え済み | ほかのエントリの `supersedes` に含まれている |
| 分岐 | 同じセッションで、同じ `prev` を持つエントリが2つ以上ある |
| 判断待ちのレビュー | review のIDを `refs` に持つ decision がない、または `保留` が残っている |
| テーマの題名 | `theme_title` が書かれたエントリ |
| テーマの現状 | テーマごとに最新の summary。ない場合は最新のエントリの「未解決・残作業」 |

## 10. 形式の検査

次の場合、`index/checks.md` に警告が出ます。

- ファイル名と `id`、フォルダ名と `theme` が一致しない
- 項目が足りない、IDの形が §2 の正規表現に合わない、`type` が5種類以外
- `prev` `forked_from` `based_on` `supersedes` `refs` に、存在しないIDがある
- review の `refs` が空
- `artifacts` の項目に name・path・url がそろっていない、または url が `https://` で始まらない
- `verbatim` に書いた原文ファイルがない
- テーマに `theme_title` が書かれたエントリがない
- 種類ごとの見出しが足りない、または順番が違う
- 保存した後のエントリや原文が変更された
- `AGENTS.md` の「変更しないもの」に挙げたファイルが変更された（ユーザーが変更した場合も表示されます）
- `themes/_unsorted/` にエントリがある

## 11. 版の管理

- この定義を変えるときは、`format` の番号を上げます。既存のエントリは書き換えず、古い版のまま残します。
- 検査は、それぞれのエントリの `format` に合わせて行います。

## 12. 例

work の例は `AGENTS.md` の末尾にあります。
